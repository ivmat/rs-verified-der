# The proof floor at `ea8dad4` — measured 2026-08-03, and `./check.sh` did NOT complete

**Headline, in the order that matters.** `./check.sh` was **OOM-killed** (rc=137) after 2308 s on
`x509_extension::proofs::validate_extensions_never_panics`, inside a computed `MemoryMax=20G` scope.
Re-running the outstanding work in split batches then established **170 of the 171 harnesses
SUCCESSFUL, 0 FAILED**, and — after a repair described below — the **L4/L5 Lean lid PASS
(sorry-free), 1704 `lake` jobs**. One harness remains unmeasured at this commit.

Nothing here says "the floor is green at HEAD", because it is not. It says exactly which 170 of 171
are green, which one is unmeasured and why, and what was broken and fixed on the way.

## 1. Why the cap was 20 GiB, and why that was never going to be enough

The cap is **computed at launch**, never a constant — a standing rule on this box since 2026-08-01,
because `MemoryMax` is a *per-cgroup* limit and a fixed cap that ignores what else is resident lets the
kernel OOM-killer pick its own victim system-wide:

```sh
AVAIL_MB=$(free -m | awk '/^Mem:/{print $7}')   # 23264
CAP_G=$(( (AVAIL_MB - 2048) / 1024 ))           # 20
systemd-run --user --scope -p MemoryMax=20G -p MemoryHigh=18G -p MemorySwapMax=0 -- ./check.sh
```

**This crate's own documentation predicted the outcome.** `PROOF_MANIFEST.md` §3.4 records
`x509_extension::validate_extensions_never_panics` peaking **~20.5 GiB**, and `README.md` says the
full floor needs *"roughly 24 GB of available RAM"*. A 20 GiB cap is **below the documented peak of
the harness that died.** So this is **not a regression and not a proof failure** — it is the
crate's stated requirement meeting a box that had ~5 GB held by desktop applications at launch
(`MemAvailable` **23264 MB** today against **26506 MB** on 2026-08-01, when the identical gate passed
under a 23 GiB cap).

Measured cgroup high-water mark before the kill: **18.77 GiB** (`memory.peak`, sampled every 5 s).
⚠ The sampler's last read is up to 5 s stale, so the true peak at kill time was higher and **is not
claimed to be known** — the only hard fact is that the cgroup limit was reached.

**The kill was reproduced, deliberately and in isolation.** Run alone in its own scope at the same
computed cap, the harness was killed again: rc=137 after 228 s. So the attribution is to that
harness, not to contention with the 162 that preceded it.

## 3. ⚠ The Lean lid was RED at HEAD, and nothing would have told us

**On its first run today the L4 lid FAILED, rc=1:**

```
== lean lid: re-extract (charon -> aeneas) + drift check ==
!! lean lid: FAIL - regenerated model differs from committed DerLengthExtract.lean.
   length.rs changed; re-extract and re-prove before committing.
```

**Cause.** Commit `f747efb` ("a runnable example on every module") inserted **414 lines of `//!`
documentation** across the crate. Aeneas embeds each definition's source span in the extracted Lean
model as a `Source: '…/length.rs', lines N:M` comment, so every one of those spans moved. All six
extracted models had drifted.

**The drift is provenance-only, and that was measured rather than assumed.** Re-extracting each model
and classifying every changed line:

| model | changed lines | of which `Source:` comments |
|---|---|---|
| `DerLengthExtract.lean` | 38 | **38** |
| `DerBigintExtract.lean` | 40 | **40** |
| `DerOidExtract.lean` | 30 | **30** |
| `DerTagExtract.lean` | 76 | **76** |
| `DerTlvExtract.lean` | 176 | **176** |
| `DerSequenceExtract.lean` | 250 | **250** |
| **total** | **610** | **610 — zero semantic** |

**The classifier was watched to fail before being trusted.** Injecting a genuine semantic change into
a committed model (`ok (self1 = other1)` → `ok (self1 != other1)` in `DerOidExtract.lean`) makes it
report `⚠ DRIFT: 32 lines, only 30 are Source: — 2 are SEMANTIC` and print them. Restoring returns
the file byte-identical by sha256 (`cfc53152…4ad8`) and the report to provenance-only. A
classification that has only ever said "harmless" is not a classification.

**Repair:** the six models were regenerated from the shipped source with the *same* commands the lid
itself uses (including the disclosed `--opaque` carve-outs and the post-extraction `Iterator` patch
for `DerSequenceExtract.lean`), and the lid then re-run in full: **`Build completed successfully
(1704 jobs)` · `== lean lid: PASS (sorry-free) ==`**, rc=0.

**Why this went unnoticed for four commits, which is the part worth generalising.** The Lean lid
lives in `check.sh`, not `check_fast.sh`, so the pre-commit gate never runs it — deliberately, since
a minutes-long proof in a blocking hook breeds `--no-verify`. But `check.sh` has not completed since
`461f751`. So between `461f751` and `ea8dad4` the L4 gate was **not red and not green: it was
unrun**, and an unrun gate reads exactly like a passing one in every summary that does not name it.
The docs commit that broke it passed every check that was actually executed.

⚠ **A second, latent defect in the lid, found while diagnosing and NOT fixed here.** The drift checks
for `length`, `bigint`, `oid` and `tag` go straight to `diff -q` with charon/aeneas output sent to
`/dev/null`. If extraction *failed* and produced no file, `diff -q` still exits non-zero and the lid
reports **"regenerated model differs … `length.rs` changed"** — blaming the source for a tool
failure. The `tlv` and `sequence` checks already guard this with an explicit `[ ! -f ]` test; the
first four do not. Today's failure was confirmed to be genuine drift by re-running extraction with
output visible (`charon` rc=0, a 318979-byte `.llbc` produced), so the diagnosis does not rest on the
unguarded path — but the next person may not be so lucky.

> **✅ FIXED later the same day — and it was not the only dead gate in this file.** All six
> extractions now check the tool's exit status and the artifact's existence before diffing, so
> EXTRACTION FAILURE and MODEL DRIFT are separate verdicts; both were watched to fire, along with a
> third mode found while fixing (a non-zero charon aborted the script with *60 bytes* of output and
> no diagnostic at all). The green run afterwards then exposed a **second** defect: the sorry-gate's
> warning arm matched `'sorry'` in single quotes while Lean 4 emits backticks, so it had never
> matched anything — and a `sorry` in a theorem without a `#print axioms` line produced
> `PASS (sorry-free)`, rc=0. Both fixed and fault-injected: **[LID-GATE-FAULTS-2026-08-03.md](LID-GATE-FAULTS-2026-08-03.md)**.

  headroom.
